# 通用接入与低配置分发（已确认需求）

状态：方案已确认，准备在新窗口进入实现。2026-09-16 用户确认目标是减少下发后的人工配置，而不仅是提供免安装 EXE；首个产品入口为 OpenCode 插件，架构需要支持后续其他工具接入。先在外网验证，再部署内网。同日用户明确“确认方案”，要求进度交接后在新窗口编码。

配套文件：[开发设计方案](../design/universal-onboarding.md)（已确认的技术基线与待落实环境信息）和[执行交接记录](../handoff/universal-onboarding/progress.md)。本文作为需求真源，按设计推荐基线实施；真实环境地址、权限和精确版本仍须查证，不能从总体方案确认中推导。

## 问题

当前便携版仍要求用户运行 setup、提供后端地址，并理解 EXE 位置和插件安装流程。对于团队下发，这些步骤依然是接入负担。已有 Windows 兼容与便携包改造可作为基础，但不作为本需求的最终交付形态。

## 已确认目标

- 首版通过 OpenCode 插件接入。
- 不修改 OpenCode 源码，不 fork、不重新编译、不替换其安装包；仅使用官方插件加载与公开接口。用户于 2026-09-16 明确补充此约束。
- 用户不需要另行运行安装脚本、PowerShell setup、配置 PATH 或填写组织后端地址。
- 已有适用凭据自动复用，新用户保留首次网页授权。
- 核心能力独立于 OpenCode；后续工具可使用相同初始化、认证、程序管理和同步核心。
- 先完成外网环境验证，再部署到内网。

## 用户故事

1. 作为使用者，我添加插件后即可进入连接流程，不需要安装独立 CLI 或寻找可执行文件。
2. 作为使用者，我不必知道后端地址、运行目录、环境变量或同步命令。
3. 作为使用者，我只在首次连接或凭据失效时进行网页授权。
4. 作为使用者，配置已经有效时，重新打开工具不会再次提示认证。
5. 作为使用者，后台同步不反复弹出终端，不因连接失败阻塞宿主工具。
6. 作为管理员，我可以为外网验证和内网部署分别提供预设配置，而无需修改业务代码。
7. 作为管理员，我能控制分发版本、制品来源、升级与回退。
8. 作为后续工具适配开发者，我复用共同核心，只实现宿主工具要求的插件或钩子入口。
9. 作为使用者，多工具并用时不会重复初始化相同环境，也不会把会话传到其他环境的后端。
10. 作为管理员，我能使用虚构会话验收完整链路，而不上传实际工作会话。

## 建议方案

### 通用核心

保留现有 Go provider、采集、脱敏、增量同步、状态管理与重试能力。将初始化和程序定位整理为面向工具适配器的稳定接口，而不是在 OpenCode TypeScript 插件中再实现一套同步引擎。

### 环境预设与分发

后端地址、环境标识、制品来源、目标平台与版本由管理员提供。外网和内网使用相同代码及协议，由环境预设决定去哪里认证、获取程序和上传。预设不包含用户 API Key。

二进制的安装位置与版本由程序管理，宿主插件通过已解析的绝对路径调用。首次下载和离线包的取舍待内网条件确认，不能默认内网可访问公网 npm、GitHub 或外部下载地址。

不同环境的凭据与同步状态需要明确隔离；不能因为发现本机已有凭据，就将其用于另一个后端。

### 工具适配器

OpenCode 首先提供其原生插件入口，负责生命周期事件、连接状态提示和启动共享核心。其他工具按各自插件/钩子机制提供适配器。

新增内容位于 Confab 的独立插件发行包中。添加插件属于宿主支持的扩展配置，不是修改宿主源码；该配置可由用户添加一次或由管理员统一预置。不能把 OpenCode 内部补丁、私有接口注入或定制版 OpenCode 作为运行前提。

“通用”指核心、配置与接入协议复用，不假设所有工具可加载同一个插件文件。插件不能顺带修改未选择接入的其他工具配置。

## 首版验收建议

- 干净的 Windows 用户环境中，无全局 confab、无 PATH 配置、无 Go 开发环境，能够从 OpenCode 插件完成首次接入。
- 使用标准安装的 OpenCode 完成验收，其程序文件和源码均不修改。
- 使用组织预设的后端地址，用户无需输入 URL 或执行 setup。
- 首次网页授权可完成；登录后能够继续设备授权，不要求用户研究终端输出。
- 重启后复用当前环境凭据，过期或不可达时给出不同状态，网络超时不误报为密钥失效。
- 新建、恢复、退出会话均可同步或正确停止；至少包括 Windows 原生启动与可见窗口观察。
- 包管理器安装和插件启动都不能无条件从公网补拉内网不可用的依赖。
- 外网验收使用明确的测试后端和虚构会话，覆盖安装、授权、上传、重试、升级与回退。
- 内网验收确认所需依赖和制品均来自允许的内网源或离线包，且不向外网发送认证或会话数据。

## 现有基础与缺口

- 已有 provider 接口支持 Claude Code、Codex、OpenCode 和 Cursor；通用性应建立在现有边界上。
- 已有设备码登录、凭据存储和后端 API；需要面向插件的初始化接口及可视状态，不只是调用交互式 CLI。
- 当前 OpenCode 插件的 npm package 仍是私有测试工程，不是可供用户添加的发行包。
- 当前正式发行配置尚未包含 Windows；需要将经过本地验证的 Windows 构建纳入新分发方案。
- 已修正 Windows 停止标记和 Git 子进程窗口问题；仍需覆盖真实宿主环境下的完整首次接入行为。
